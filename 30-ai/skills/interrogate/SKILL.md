# Interrogate

原典:
https://github.com/cursor/plugins/blob/main/pstack/skills/interrogate/SKILL.md

変更や設計を壊す条件を探す。

指摘は実際の実行で証明された場合にのみ採用する。
レビュー結果を報告し、修正は適用しない。

## 対象の確定（Frame）

対象範囲はユーザーの指定を優先する。

指定がなければ、基準ブランチとのマージベースから現在のブランチと作業ツリーまでの差分を対象とする。

ユーザーの依頼、コミット、PRの説明を確認し、`in-your-own-words` を使って変更の目的を整理する。

目的を特定できない場合は確認する。

## 並列レビュー（Fan out）

`arena` の以下の手順を利用する。

- Phase A の実行担当選定と作業領域の分離
- Phase B の並列実行

ただし、次の点を変更する。

1. 各レビュー担当に同じ対象範囲と実装意図を渡す。
2. 未コミットの変更も各担当の独立した作業領域へ反映する。
3. 各担当は問題の発見と再現に集中する。
4. 実装の優劣ではなく、証明された欠陥を収集する。

各担当には次の内容を指示する。

「この変更を壊す条件を探す。

実際のコードに対する失敗テスト、再現スクリプト、実行コマンドなどを使い、指摘を証明する。

設計や計画が対象なら、試作品を実行するか、既存コードに対して検証する。

再現用の変更は担当者ごとの独立した作業領域に残す。

各指摘には以下を含める。

- 問題の名前
- 実行したコマンド
- 実際の出力
- 実装意図から期待される出力

実行による証拠がない指摘は含めない。
指摘がゼロでもよい。」

## 検証（Verify）

`arena` の Phase F と同じように、各指摘の実行コマンドを再実行する。

- 実際に失敗が再現することを確認する。
- 失敗が実装意図に反することを確認する。
- 証明できない指摘は除外する。
- 同じ根本原因による指摘はまとめる。

`arena` の Phase C、D、E は実行しない。

異なるレビュー担当から複数の欠陥が見つかった場合は、証明されたすべての問題を残す。単一の案を選ぶ必要はない。

## 報告（Output）

### 目的

変更によって実現するべき振る舞いを記載する。

### 検証済みの問題

各問題について以下を報告する。

- 問題の内容
- 実行したコマンド
- 実際の出力
- 期待する出力
- 実装意図に反する理由
- 問題を発見したレビュー担当

検証された問題がなければ、その旨を報告する。

### 除外した指摘

各担当について、除外した指摘の件数と理由を報告する。

## 実行環境に関する制約

複数のサブエージェントを利用できない場合は、単一エージェントで同じ検証手順を実施し、その制約を報告する。

モデルは固定しない。

ファイル変更やGit操作については、ルートのAGENTS.mdに定義された権限を優先する。
